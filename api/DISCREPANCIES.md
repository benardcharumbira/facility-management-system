# Where a slice prompt and its handler disagreed

Each slice prompt described the endpoints it expected. Where the implemented handler differs, **the handler wins**, because it is what the frontend actually calls. Each of these is a decision somebody made while building and did not write down; they are written down here so the backend developer is not surprised.

## Gaps in the API surface

Recorded, not filled, as this slice asked.

- **No operation reads one booking’s audit history for the applicant.** A booking carries a `history` the applicant sees; the full trail is the audit endpoint, for system administrators.
- **No read of a single seating arrangement, event type or terms version by id.** The lists are small and return everything; the client never needs one.
- **No pagination on the vocabularies, terms and blackouts.** They are plain arrays. If any grows, it becomes an envelope and that is a breaking change.
- **No operation to edit the public static pages.** `GET /public/content/{slug}` serves them; how the municipality changes them is not specified (out of scope for slice 12).
- **The contact telephone number is not yet shown to approvers.** It is stored; no approval or booking response carries it (Q41).
